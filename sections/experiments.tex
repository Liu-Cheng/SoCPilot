\section{Experiments}
\label{sec:evaluation}

We evaluate SoCPilot from system outcomes to the mechanisms behind them. After describing the common setup, we report complete-application acceleration and examine the selected architectures and kernel measurements to explain the gains and remaining costs. We then compare the automation achieved by SoCPilot and a general-purpose agent using the same LLM. Targeted analyses finally examine reusable-IP selection and area-budget sensitivity.

\subsubsection{Paired baselines and measurement scope}
For each application, the CPU-only baseline executes all processing stages in software on the selected CPU. Its paired CPU--accelerator implementation uses the same CPU, cache parameters, clock, compiler settings, and input, with selected function calls replaced by accelerator invocations. WAMI uses the 3-mm$^2$ Ibex configuration for this paired comparison. Cycle counters retain both 32-bit halves before conversion to milliseconds at 75~MHz; serial-receiver timestamps are not used for timing.

Reported application latency uses the instrumented board-cycle intervals. For WAMI, the measured input conversion/packing interval is subtracted; for nightvision, the measured input-quantization interval is subtracted. These operations still execute. Nightvision DMA packing, output unpacking, cache synchronization, and start-to-done waiting remain included. Plate recognition, recognition, and scan use their full measured intervals. Application speedup divides the paired CPU-only total by the reported accelerated total; the same timing definition applies throughout the figures and budget study.

For each mapped function, kernel speedup compares its software-call latency in the CPU-only run with its replacement-stage latency in the CPU--accelerator run.

Application and kernel speedups use board measurements. The supplied logs report reference verification as unchecked. Their output signatures provide execution fingerprints, not proof of numerical equivalence to the original floating-point application. In particular, WAMI and nightvision use fixed-point accelerator representations. Area budgets and DSE estimates share the analytical model's technology basis. We independently report synthesis-derived standard-cell and SRAM-macro area normalized to a common 45-nm-equivalent basis, excluding only the 1000-KiB application RAM. This is a normalized cell-area comparison, not a measurement of post-route die area.

\subsubsection{Application acceleration}

\subsubsection{Kernel acceleration and CPU-resident work}
Figure~\ref{fig:hotspot_stage_speedups} shows the seven mapped kernels in the current configurations. All seven reduce their replacement-stage latency under the stated timing scope.

\begin{figure*}[t]
\centering
\includegraphics[width=\textwidth]{pic/hotspot-stage-speedups.pdf}
\caption{Board-measured speedups of the seven mapped kernels. Each ratio is CPU-stage latency divided by hardware replacement-stage latency, using the timing definition in the setup. Invocation, DMA, synchronization, and output conversion remain included. The dashed line marks 1$\times$.}
\label{fig:hotspot_stage_speedups}
\end{figure*}

For recognition, scan, and nightvision, the mapped functions account for 76.58\%, 77.05\%, and 67.21\% of CPU-only runtime, respectively. Plate recognition's closing stage accounts for 50.01\% of baseline runtime and accelerates by 15.91$\times$; top-hat and black-hat remain CPU-resident and take approximately 2.07 and 2.10~s in either execution. These remaining stages limit application speedup to 1.88$\times$ despite the faster closing stage.

\paragraph{WAMI: kernel gains and CPU-resident work}
In the paired 3-mm$^2$ Ibex configuration, the reported \texttt{warp\_image} stage falls from 52,425.388 to 1,556.415~ms and \texttt{hessian} from 16,500.429 to 82.082~ms. The software-only \texttt{steepest\_descent} takes 6,287.612~ms in the accelerated application, versus 5,991.832~ms in the CPU-only run.

The large kernel gains therefore do not translate directly into the same application-level gain: CPU-resident stages and runtime work remain in the execution path. A performance model based mainly on HLS cycles and payload divided by bandwidth needs CPU-dependent estimates for invocation, output conversion, cache maintenance, synchronization, and remaining software processing to capture these costs.

\subsection{Automation Comparison with a General-Purpose Agent}
\label{subsec:general_agent}
We test whether a general-purpose agent equipped with the same underlying LLM can achieve the level of design automation supported by SoCPilot. Both workflows use DeepSeek-v4-pro on the five applications. Following the HSCO-Bench~\cite{hscobench2026} protocol for the general-purpose baseline, we assess whether the agent can complete the required accelerator implementation, verification, synthesis, and SoC integration tasks, and record the stage reached in each run.

The general-purpose agent receives each migrated application's source, the HSCO-Bench template, and access to Catapult HLS, SystemC, MatchLib, ESP, and Vivado for the ZCU102 target. It must select and implement its accelerator and prepare the required driver and ESP configuration. Each run ends on completion, agent-budget exhaustion, or failure at a required stage. Figure~\ref{fig:hscobench_stage_outcomes} reports device-ID checking, behavioral-simulation compilation, execution and verification, and Catapult HLS.

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{pic/hscobench-stage-outcomes.pdf}
\caption{Automation outcomes of the general-purpose agent using the same DeepSeek-v4-pro model as SoCPilot, following the HSCO-Bench protocol. Blue indicates a passed stage, orange the observed failure, and gray a later stage not reached.}
\label{fig:hscobench_stage_outcomes}
\end{figure}

The general-purpose agent completes the required generation tasks for none of the five applications. Nightvision and plate recognition encounter compilation failures during behavioral simulation; scan fails output verification. Recognition and WAMI pass behavioral simulation but encounter HLS synthesis failures. SoCPilot reaches accelerator generation, HLS synthesis, ESP integration, and FPGA application execution for all five workloads, using the fixed embedded runtime described in the experimental setup. The original HSCO-Bench study reports a \texttt{NightVision} speedup of 1.08$\times$ with Claude Opus 4.6~\cite{hscobench2026}. Our current paired nightvision measurements yield 2.08$\times$. The cross-study figures use different experimental settings and do not constitute a controlled performance comparison.

For these applications and experimental settings, the tested general-purpose agent does not match SoCPilot's task-completion level despite using the same LLM. The results support the value of SoCPilot's domain-specific task decomposition, explicit design representations, and tool-feedback loops in coordinating the design tasks.

\subsubsection{Measured WAMI area-budget sensitivity}
\label{subsec:area_aware}
We examine seven deployed WAMI configurations selected at 1.8, 2.2, 3, 4, 8, 9, and 10~mm$^2$ budgets. Each independent search uses 40 initial samples and 20 optimization iterations, reusing the prepared accelerator candidates and DMA interfaces while exploring CPU, cache, and HLS parameters. Table~\ref{tab:wami_budget_configs} records the exact selections and synthesis-derived areas; Figure~\ref{fig:wami_area_budget} plots board measurements rather than predicted DSE latency. Each reported latency is one supplied board execution, not an average over repeated trials. All WAMI runs use three frames, 20 iterations, and 183/60/60 calls to warp, steepest descent, and Hessian, respectively.

The selected mapping grows from CPU-only at 1.8~mm$^2$, to Hessian at 2.2~mm$^2$, and Hessian plus warp at 3 and 4~mm$^2$. The CPU changes from Ibex to LEON3 at the 4-mm$^2$ point, and to Ariane with all three kernels accelerated at 8, 9, and 10~mm$^2$. The measured latency falls from 44,161.522~ms at 1.8~mm$^2$ to 1,574.521~ms at 4~mm$^2$, but rises to 1,711.761 and 1,705.779~ms at 8 and 9~mm$^2$. Increasing the area ceiling therefore does not guarantee a faster deployed configuration.

The 8-mm$^2$ Ariane selection is 8.72\% slower than the 4-mm$^2$ LEON3 selection. Its Hessian and warp replacement stages take 386.069 and 490.611~ms, compared with 59.795 and 407.494~ms on LEON3. Hardware steepest descent is faster (358.781 versus 401.416~ms in software), but that gain does not offset the other stage costs. An additional measured 6-mm$^2$ Ariane selection, outside the plotted subset, takes 1,692.365~ms and is also slower than the 4-mm$^2$ selection. These are comparisons between complete selected configurations: HLS settings, DMA width (64 versus 32 bits), cache organization, and fixed-point representation also change. Replacement-stage timers retain DMA, control, synchronization, and output conversion; they do not isolate accelerator compute cycles. Aggregate timings alone cannot establish which individual mechanism causes the slower stages.

The 10-mm$^2$ Ariane configuration is instead faster: 1,438.816~ms, or 8.62\% below the 4-mm$^2$ LEON3 time. Compared with the 8-mm$^2$ selection, its LLC increases from 8 to 64~KiB and its cache line from 32 to 64~B, while L2 decreases from 32 to 16~KiB. Total latency improves by 272.945~ms; 223.691~ms of this reduction lies outside the three accumulated kernel-stage intervals. This localizes much of the improvement to remaining application/runtime work, but attributing it specifically to cache misses or bandwidth would require additional counters. Normalized synthesis area increases from 5.565 to 8.991~mm$^2$ across these two selections. The searches minimize predicted latency under a model-area ceiling, not measured board latency, and run independently without preserving earlier best configurations. Model error and finite search coverage thus limit any claim of monotonicity or global optimality.
