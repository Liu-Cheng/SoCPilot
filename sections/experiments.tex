\section{Experiments}
\label{sec:evaluation}

We evaluate SoCPilot's ability to transform high-level C/C++ applications into customized CPU--accelerator SoCs and improve application performance. First, we compare its design-generation outcomes with a general-purpose agent following the HSCO-Bench protocol, examining the stages completed and the higher completion rate achieved by SoCPilot. We then compare the generated CPU--accelerator systems with matched CPU-only baselines to quantify end-to-end application speedups. Finally, we analyze the hotspot functions extracted by SoCPilot and their acceleration results to understand how individual hardware-mapped functions contribute to application-level performance.

\subsubsection{Baselines and measurement protocol}


Each generated SoC is compared against an application-specific paired CPU-only baseline. After SoCPilot selects the CPU type and memory-system parameters, the matched CPU-only configuration retains the same CPU, cache configuration, clock target, compiler, input data, and application algorithm, but executes the selected hot functions on the CPU rather than invoking accelerators. This paired comparison isolates the end-to-end latency benefit of accelerator integration from differences in CPU choice, cache configuration, compiler settings, or application inputs.

Reported total latency covers the complete baremetal application execution, including CPU computation, accelerator invocation, cache flushing and synchronization, and all functions that remain on the CPU. Per-accelerator latency is measured only over the accelerated kernel region, from accelerator configuration and launch to completion detection. A result is considered functionally correct only when the hardware output matches the corresponding CPU or golden reference.

\subsection{Comparison with a General-Purpose Agent}
\label{subsec:general_agent}

We first compare SoCPilot's structured workflow with a general-purpose LLM agent following the HSCO-Bench~\cite{hscobench2026} evaluation protocol. This comparison asks whether an open-ended agent can progress through acceleration-target identification, implementation, functional verification, HLS synthesis, and ESP integration for the same application workloads.

\textbf{General-agent execution protocol.}
We instantiate the general-purpose-agent baseline using DeepSeek-v4-pro as the underlying LLM. DeepSeek-v4-pro is not among the five frontier models evaluated in the original HSCO-Bench study; therefore, our experiment represents an independent execution of the HSCO-Bench protocol rather than a reproduction of one of its reported model configurations. For each application, the agent is provided with the migrated benchmark workspace, including the application source code, the HSCO-Bench template structure, and access to the local hardware/software co-design toolchain. The target platform is configured as Xilinx ZCU102 (\texttt{xilinx-zcu102-xczu9eg}) within the ESP infrastructure, and all applications use a consistent tool environment comprising Catapult HLS, SystemC, MatchLib, ESP, and Vivado.

The general-purpose agent must independently identify an acceleration target, construct the corresponding accelerator within the HSCO-Bench template structure, integrate the required software-driver and ESP configuration entries, and produce a workspace accepted by the benchmark flow. Each run terminates when the agent completes the evaluated workflow, exhausts the configured agent budget, or encounters a failure at a required tool-flow stage. As shown in Table~\ref{tab:hscobench_results} and Figure~\ref{fig:hscobench_stage_outcomes}, the general-purpose agent fails at different stages across all five applications. The observed failures span source-level type correctness, functional equivalence, and HLS compatibility. For \texttt{nightvision} and \texttt{plate\_recognition}, the generated implementations fail during BEV-Sim compilation because of invalid C++ type operations. The \texttt{scan} implementation proceeds further but fails functional verification because its output differs from the software reference. The \texttt{recognition} and \texttt{wami} implementations both pass behavioral simulation but fail during Catapult HLS because of synthesis-related language or scheduling constraints. These results indicate that successfully generating an accelerator candidate does not by itself guarantee progression through the subsequent verification and synthesis stages. In comparison, SoCPilot completes accelerator generation, HLS synthesis, ESP integration, and FPGA-based application execution for all five applications.


\textbf{Comparison with published HSCO-Bench results.}
The original HSCO-Bench study provides additional context for two workloads that overlap with our evaluation. Among the five frontier models evaluated in that study, \texttt{NightVision} was successfully accelerated only by Claude Opus 4.6, achieving a reported 1.08$\times$ speedup, whereas \texttt{WAMI} was a consistent-failure case for which none of the evaluated models produced a valid accelerated design~\cite{hscobench2026}. Our separately configured board evaluation reports 2.03$\times$ end-to-end speedup for \texttt{nightvision} and 1.77$\times$ for \texttt{wami} in Figure~\ref{fig:e2e_speedup_comparison}. These values provide context, not a controlled cross-platform speedup comparison, because the hardware platforms and experimental configurations differ. The stronger conclusion from this experiment is that the general-purpose agent did not complete the required HSCO-Bench tool flow on these five migrated workloads, while SoCPilot reached FPGA execution for all five applications, with the verification limits discussed in Section~\ref{subsec:e2e_evaluation}.

\paragraph{WAMI stage slowdown}
The updated WAMI pair processes three $32\times32$ frames with 20 Lucas--Kanade iterations and reports identical invocation counts: 183 for \texttt{warp\_image}, 60 for \texttt{steepest\_descent}, and 60 for \texttt{hessian}. Warp and Hessian stages improve by 3.20$\times$ and 1.95$\times$, respectively, but \texttt{steepest\_descent} increases from 3018.276 to 3700.943~ms: a 0.82$\times$ speedup, or 22.62\% longer execution. Its aggregate penalty is 682.667~ms, approximately 11.378~ms per invocation. The gains elsewhere still reduce total latency from 30225.590 to 17112.106~ms (1.77$\times$). Thus, application-level improvement does not imply that every hardware-mapped stage benefits.

The WAMI wrapper times each hardware stage from input conversion and packing through register setup, cache maintenance, completion polling, and output conversion; the CPU interval covers the corresponding CPU function. These are replacement-stage costs, not isolated accelerator compute latencies. For \texttt{steepest\_descent}, two gradient inputs produce six output components per pixel. At $32\times32$ with one 32-bit value per word, this entails 32~KiB of input/output payload per call, in addition to CPU-side format conversion and synchronization. For this relatively lightweight kernel, these costs can outweigh the compute benefit. Phase-separated memory access used to avoid bridge deadlock can also limit read/compute/write overlap. These are plausible explanations, not measured bottleneck attributions: the log does not separate conversion, cache maintenance, DMA, and RTL compute time. Component-level timing is needed before assigning a dominant cause or changing the mapping. The selected DSE model predicts 3.66$\times$ application speedup, whereas the board measures 1.77$\times$; hardware-mode latency is 2.03$\times$ the modeled value.

All five updated timing logs report image~1 at 75~MHz with \texttt{verification=unchecked} and \texttt{mismatches=-1}. The CPU and hardware runs have matching reported output signatures for \texttt{plate\_new}, \texttt{recognition}, and \texttt{scan}; \texttt{plate\_new} and \texttt{recognition} both report no detected target for this input. The updated Leon3 \texttt{nightvision} runs each execute 24 convolution calls and report identical signatures: \texttt{0x4a6baff8}, \texttt{0x4a6a83b9}, and \texttt{0x4a711a54}. WAMI reports zero foreground in both modes, but its model signatures differ (CPU: \texttt{0x465ddfc0}; hardware: \texttt{0x465de02f}), and \texttt{original\_float\_exact=-1} does not establish equivalence to the floating-point reference. These records establish board execution and timing, but do not establish full reference-output equivalence or application quality over a dataset.

\subsubsection{Hotspot Selection Comparison}
\label{subsec:hotspot_comparison}
To isolate the effect of hotspot selection, we compare SoCPilot's profiling and HLS/cost-based candidates with a source-only LLM baseline. The LLM receives the application source and design constraints but no SoCPilot profiling or PPA results, and nominates up to three functions. Its nominated functions are re-evaluated in a separate workspace using the same CPU/cache configuration as the corresponding SoCPilot map. Both candidate sets then pass through the same communication-aware mapping algorithm, performance estimator, and area limit. We compare the nominated functions, functions ultimately mapped to hardware, validity under the area constraint, and estimated application latency. This comparison stops after the initial map and PPA evaluation; it does not repeat system-level DSE or FPGA deployment.

\subsubsection{Nightvision Area--Latency Trade-off}
\label{subsec:area_aware}
We examine sensitivity to area budgets ranging from 3 to 16~mm$^2$ while keeping the accelerator mapping fixed to \texttt{conv2d}. Each budget uses an independent HyperMapper search with 90 initial samples and 30 optimization iterations. We record the selected CPU, accelerator configuration, estimated area, and estimated latency at each budget. These trade-off points use analytical area and performance models rather than FPGA resource utilization or board measurements. The search varies CPU type, cache parameters, and HLS pipeline settings; loop-unroll factors remain one in this sweep. The objective is model-estimated complete-application latency under the total-area constraint, using average-case HLS latency for the accelerator.

\label{fig:nightvision_area_latency}
\end{figure}

Figure~\ref{fig:nightvision_area_latency} shows the latency and estimated total area of the selected configurations for budgets from 3 to 11~mm$^2$. At 3~mm$^2$, the selected Ibex configuration occupies an estimated 1.656~mm$^2$ and takes 1161.38~ms. Raising the budget to 4~mm$^2$ selects Leon3 at 3.970~mm$^2$ and 138.21~ms, an 88.1\% reduction in predicted latency. Leon3 remains selected at 5~mm$^2$, while Ariane is selected from 6~mm$^2$ onward. Panel (b) distinguishes the budget from the estimated area used: for example, the design selected under the 8-mm$^2$ budget occupies 6.932~mm$^2$. Beyond the architectural transitions, larger designs yield diminishing returns: from the 7- to the 11-mm$^2$ budget, selected area grows from 6.925 to 10.264~mm$^2$ (48.2\%), while latency falls from 132.22 to 132.00~ms (0.17\%). The full sweep extends to 16~mm$^2$; its best result above 11~mm$^2$ is 131.98~ms, improving on the 11-mm$^2$ result by less than 0.02\%. We therefore focus the figure on the range containing the main architectural transitions.

The cache configurations account for the later area growth. Across the Ariane points, the calibrated L1 instruction and data caches retain capacities of 16 and 32~KiB and associativities of four and eight, respectively; only their common line size follows the DSE setting. At the 7-mm$^2$ budget, L2 has 256 sets and four ways (32~KiB), and LLC has 512 sets and eight ways (128~KiB), both with 32-byte lines. At 11~mm$^2$, L2 has 512 sets and four ways (128~KiB), and LLC has 1024 sets and four ways (256~KiB), both with 64-byte lines. Their combined McPAT area rises from 1.625 to 4.964~mm$^2$, while the fixed CPU area (5.224~mm$^2$) and selected accelerator area (0.077~mm$^2$) are unchanged. Thus, the larger cache configurations account for the 3.339-mm$^2$ area increase between these two points. Capacity alone does not determine the estimate: the 9- and 11-mm$^2$ points have the same L2/LLC capacities, but different line sizes and LLC associativities.

The timing model also explains the limited benefit. Between the 7- and 11-mm$^2$ points, simulated CPU-only time decreases only from 535.674 to 534.474~ms. After subtracting the mapped hotspot using the recorded profiling weight, the model's residual CPU contribution falls from 99.582 to 99.359~ms; the aggregate HLS contribution remains 32.639~ms. These terms account for the 0.223-ms end-to-end reduction. The fixed \texttt{conv2d} mapping and unit unroll factors limit the explored changes to the existing architecture rather than additional hotspot offloading. This decomposition describes model sensitivity; it does not establish a measured cache-miss or memory-bandwidth bottleneck, and jointly varied cache and HLS settings do not isolate individual parameter effects.


The DSE objective minimizes latency subject to a hard area ceiling, with smaller area breaking exact latency ties. Consequently, even a small predicted latency gain can select a substantially larger design. The small reversals at 8 and 10~mm$^2$ reflect independent 120-evaluation searches; earlier feasible designs are not carried forward as incumbents. These are best sampled results rather than global optima, and a larger budget does not guarantee that an independent search discovers a better point. All reported latencies and areas in this sweep are model estimates rather than FPGA measurements.
